# 药品/器械/政策平台数据库建设方案——可行性评估与落地路线

> 基于《数据库搭建.txt》（第三方 AI 方案）与本仓库现状（drug-tool 前端 + policy-crawler 爬虫/API）
> 评估日期：2026-08-25

## 1. 总体结论

第三方方案**方向正确、诊断准确，但明显过度设计**。它的核心判断（localStorage 无主键无 schema、
政策两套模型、后端闲置、人工录入不可持续）与代码事实完全一致，主架构（PostgreSQL + FastAPI +
爬虫自动采集 + 人工审核兜底）也与本仓库已有实现同构，可以直接采用。

需要砍掉的：分库分表、ES、Redis 集群、Neo4j、Patroni、Airflow、代理池、验证码平台——
当前数据规模（几十万行级别）单实例 PostgreSQL 绰绰有余，这些会拖垮单人开发进度。

需要修正的：**批准文号不能当药品唯一主键**；"是否进医保"不是布尔值；
"作用机制/适应症"没有官方结构化数据源，是全项目最重的人工环节。

| 项目 | 评估 | 说明 |

## 3. 关键修正：数据模型核心设计

### 3.1 主键分层（最重要）

```
drug.product       品种层：通用名+剂型+规格+企业（组合去重）
  └── drug.registration  注册层：批准文号/注册证号（一品种多文号，状态独立）
        └── drug.insurance_entry  医保目录条目（按目录版本，多对多）
```

业务去重键建议：`generic_name + dosage_form + specification + manufacturer_norm`；
注册层以 `approval_number` 唯一；无文号的（中药饮片、院内制剂等）用 `TEMP-` 前缀临时键。

### 3.2 核心表清单（drug / device / policy / common 四域）

**common（公共）**
- `data_source`：来源注册（NMPA/CDE/医保局/卫健委…）
- `crawl_log`：爬虫任务日志（复用现有 crawler_logs）
- `attachment`：说明书 PDF、政策原文附件元数据

**drug（药品）**
- `product`：品种主档（通用名/剂型/规格/企业/ATC/类型/OTC 标志/说明书附件/来源/核验状态）
- `registration`：批准文号、注册日期、有效期、状态（有效/注销/停产）、上市许可持有人
- `indication`：适应症（可多条、按版本，`is_current` 标志）
- `mechanism`：作用机制（靶点、机制描述）
- `ingredient`：成分（名称/含量/单位）
- `insurance_entry`：医保条目（目录版本/甲/乙/谈判/编码/限定支付范围/价格/生效与失效期/`is_current`）
- `change_history`：变更历史（批准变更、说明书修订、医保调整）

**device（器械）**：`product`（注册证号/产品名/管理类别/预期用途/结构组成/企业）、
`registration`、`insurance_entry`（耗材医保条目）、`change_history`

**policy（政策）**
- `base`：标题/机构/日期/文号/类型/摘要/全文/附件/来源 URL（`source_url` 唯一去重）
- `drug_relation`：政策-药品关联（关系类型/置信度/人工确认标记）
- `device_relation`：政策-器械关联

### 3.3 医保建模要点

"是否进医保"必须回答四个问题：**哪个版本的目录？甲/乙/谈判？限定支付范围是什么？
当前是否有效？** 因此：

- 建 `insurance_catalog` 目录版本表（版本号/发布日期/来源）
- `drug.insurance_entry` 每条记录带 `catalog_version` + `category`（甲/乙/谈判/双通道）
  + `payment_scope` + `effective_date/expire_date`
- 前端展示"医保状态"时默认取 `is_current=TRUE` 且目录为最新版，历史版本留档

## 4. 数据采集策略（按数据难度排序）

| 数据 | 官方来源 | 采集方式 | 更新频率 | 难度 |
| --- | --- | --- | --- | --- |
| 政策全文 | NMPA/NHSA/NHC 官网 | ✅ 已有爬虫 | 日更（Actions） | 低 |
| 药品注册信息 | NMPA 药品查询、CDE 上市目录集 | 官方检索接口/页面 + 增量解析 | 周更 | 中 |
| 医保目录 | 国家医保局目录（PDF/Excel） | 文件解析导入 + 版本化 | 年更 + 谈判动态 | 中 |
| 器械注册 | NMPA 器械查询 | 同药品模式 | 月更 | 中 |
| 说明书正文 | NMPA/CDE 附件 PDF | PDF 解析 + OCR | 随药品录入 | 高 |
| 适应症/机制 | 说明书 + 专业整理 | **AI 半自动抽取 + 药师人工审核** | 人工推进 | 高 |
| 政策-药品关联 | 政策全文 + 品种库 | 关键词/实体识别 → 人工确认 | 随政策更新 | 中 |

结论：**"人工录入为主"作为唯一方式不可行，但"人工审核兜底"必须保留。**
推荐模式：自动采集 80% → 清洗标准化 → 关键字段（适应症/医保状态）人工核验 →
`is_verified` 标记 → 前端只展示"已核验 + 来源 + 更新时间"。

## 5. 部署两条路线（明确取舍）

GitHub Pages 是纯静态托管，跑不了数据库和 API。两条路线：

**路线 A：托管后端（推荐中期）**
Supabase 免费层（PostgreSQL + REST + 认证）或 Neon 免费层 + Render/Railway 部署 FastAPI。
优点：真正的多用户、实时更新；缺点：免费层有配额，需维护。

**路线 B：离线 ETL + 静态快照（推荐短期，已跑通）**
PostgreSQL/SQLite 作为本地主库 → 每日 ETL 输出 `data/drugs.json`、`data/policies.json` 快照
→ 提交推送到 GitHub Pages。优点：零运维零成本；缺点：只读、更新有延迟、无多用户。

建议：**先用路线 B 把数据管道做扎实，同时把 schema 设计成路线 A 可直接迁移**；
老百姓查询站上线前再切路线 A。

## 7. 合规与责任红线

1. 药品/器械信息面向老百姓展示时，必须标注"仅供参考，不构成诊疗建议，请遵医嘱"，并显示数据来源与更新时间。
2. 政策引用注明原始出处链接；爬虫遵守 robots.txt 与请求频率（现有合规基线已内置）。
3. 说明书、医保目录为公开文件可整理引用，但不得整体搬运商业数据库内容。
4. 核心字段（适应症、医保状态）未经人工核验不得标记为"已核验"，前端需区分展示。
